# Assignment 2 — Q5: Generic Team Leaderboard

## Aim

Implement a reusable `Leaderboard<T>` that ranks teams using an injected comparator, returns a sorted copy, and leaves its stored insertion order unchanged.

## Prediction

The comparator chain should rank by points descending, goal difference descending, and name ascending. Eagles should lead with six goals of difference. Bisons and Panthers share the next two criteria, so the alphabetical name tie-break puts Bisons first. A points-only comparator should fail to impose that required order.

## Design and test data

- `Team` stores a name, points, and goal difference.
- `Leaderboard<T>` stores entries and accepts a `Comparator<? super T>`. `addAll(List<? extends T>)` accepts a list of the element type or a subtype. `sortedCopy()` copies the list before sorting and returns that separate list; `originalEntries()` also returns a defensive copy. `LeaderboardDemo` is the entry point; `ComparatorDemo` demonstrates the ranking comparator directly.
- The standings comparator is built with `Comparator.comparingInt(...).reversed()`, `thenComparing` for descending goal difference, and `thenComparing` for ascending team name.
- Main standings input, in insertion order: Panthers(9,4), Cobras(6,1), Bisons(9,4), Eagles(9,6).
- Tie tests cover equal points and goal difference (name decides), and completely equal keys (stable sorting preserves insertion order). A deliberately faulty points-only comparator sorts Panthers before Bisons when that is the input order, demonstrating the missing tie-break.

## Procedure

Compiled every Java source in `Q5` and `Q6` with Java 17 and `javac -Xlint:all`; ran `Q5Demo`. The program checks the exact standings, verifies the leaderboard's stored order is unchanged, verifies changing a returned list cannot change stored entries, and runs both tie tests and the faulty-comparator demonstration.

## Alternatives and complexity

- **`Comparable<T>`:** useful when one natural ordering is intrinsic to every instance. It would put ranking policy inside `Team`, making alternate rankings less convenient. `Team` has no such universal natural order here.
- **`Comparator<T>`:** keeps ranking policy external and composable. The chained comparator states all three criteria explicitly and can be changed without modifying `Team`.
- **Stable multi-pass sorting:** Java's `List.sort` is stable, so sorting by name, then goal difference descending, then points descending can produce the same result if every pass is stable and performed in that least-to-most-significant order. A single comparator chain is clearer, performs one sort, and avoids depending on several coordinated passes. If every comparator key is equal, the stable sort keeps the existing order.
- Adding an entry is amortized **O(1)**. `sortedCopy()` copies **O(n)** entries and sorts in **O(n log n)** comparisons (Java's list sort); it uses **O(n)** additional list storage. Comparisons are constant time for numeric keys, plus name comparison proportional to the compared name prefix.
