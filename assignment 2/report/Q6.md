# Assignment 2 — Q6: Severity-Based Patient Queue

## Aim

Represent patients with a name, severity from S1 (highest urgency) through S5, and monotonically increasing arrival counter. Serve lower severity numbers first and preserve arrival order among equal severities.

## Prediction

A Java `PriorityQueue` ordered by severity ascending and then arrival ascending should produce the requested six-patient order. It should have logarithmic admission and removal; a sorted linked list should have linear admission and constant-time removal; five FIFO queues should be efficient for this fixed five-level severity scale.

## Design and test data

`Patient` is immutable and validates severity and arrival values. `Triage` provides a reusable priority-queue service; `TriageDemo` exercises that class, while `Q6Demo` compares three implementations. `PriorityQueueDemo` and `ArrayQueueDemo` are runnable entry points for those comparisons.

1. `PriorityQueue<Patient>` with `severity` ascending, then `arrival` ascending.
2. A sorted `LinkedList<Patient>`, inserting before the first lower-priority patient and removing from its head.
3. Five FIFO `ArrayDeque` buckets, one per severity; removal scans S1 through S5 and polls the first non-empty queue.

The six-patient demonstration admissions are Meena(S1), Kumar(S1), Lata(S2), Ravi(S3), John(S3), Asha(S5), with arrival counters 0–5. A separate eight-patient check appends Nisha(S1) and Omar(S3), counters 6 and 7; expected discharge order is Meena, Kumar, Nisha, Lata, Ravi, John, Omar, Asha. This makes the same-severity FIFO rule checkable at both S1 and S3.

## Procedure

Compiled all Java files in `Q5` and `Q6` using `javac -Xlint:all`, then ran `Q6Demo`. Each implementation is checked against the exact six-patient output and the eight-patient hand check.

For timing, `Q6Benchmark` creates seeded, uniform S1–S5 patient datasets of 1,000, 10,000, and 100,000 arrivals. Each implementation receives the exact same pre-generated dataset for a given size. To avoid the impractical quadratic cost of filling a sorted list with 100,000 simultaneous residents, this is a **bounded-residency throughput experiment, not a full-occupancy scaling test**: the dataset is handled in batches of at most 256 arrivals, and each batch is completely discharged before admitting the next. Thus each run performs N admissions and N removals with peak occupancy 256 (or less for smaller runs); the same batching and data are used for all three alternatives. This keeps the sorted-list baseline feasible while retaining its normal sorted insertion and removal operations. Results must not be extrapolated to a 100,000-patient queue resident all at once.

The benchmark runs three unmeasured warm-ups and seven measured repetitions per size and implementation. Dataset generation and queue construction are outside the timed regions. Separate `System.nanoTime()` intervals accumulate admission and removal time over all batches; the CSV saves each measured trial separately, and the table below is the mean across its seven trials. No sorting pass is substituted for queue admission, and all alternatives process the same priority distribution and arrival order. The measured run is saved to `Q6/results.csv` and copied to `experimental-data/Q6-results.csv`; `Q6/plot_benchmark.py` regenerates the graph from the raw CSV.

## Alternatives and complexity

| Structure | Admission | Remove next patient | Notes |
|---|---:|---:|---|
| `PriorityQueue` | **O(log n)** | **O(log n)** | `peek()` is O(1); unordered iteration does not print patients in priority order. Repeated `poll()` or copying then draining is needed for ordered output. |
| Sorted `LinkedList` | **O(n)** | **O(1)** | Admission traverses to the insertion point; head removal is cheap. It keeps a fully sorted list at the cost of linear insertion. |
| Five FIFO queues | **O(1)** | **O(1)** for five fixed levels | Admission appends to one severity queue; removal scans up to five queues. FIFO is intrinsic within each severity. If the number of priority levels grows, the scan is O(k), or a separate index can be used. |

All three alternatives require O(n) space for n waiting patients; the five-bucket variant also has O(k) queue references for k severity levels (five here).

The exact fixed five-level system makes the bucket approach attractive. A priority queue is also a suitable general-purpose choice for a clinic handling approximately 5,000 admissions per day: logarithmic queue operations scale well, and 5,000 admissions alone is not a large heap. Choose five buckets if the severity scale will remain fixed and strict FIFO within a severity is the complete policy; choose the heap when priorities may expand or become more general.

Continuous arrivals of the most urgent patients can starve less urgent patients in every strict-priority design. Ageing can mitigate this by improving an old patient's effective priority after a wait threshold, but this changes strict medical-severity ordering; an implementation must preserve emergency overrides and define the clinical policy carefully. `PriorityQueue` does not reorder an element when its comparator fields change, so ageing would require reinsertion or a separate scheduling mechanism.

## Result

All three implementations produced the requested exact output and passed the independent eight-patient FIFO check. The bounded benchmark completed for every requested size, with real measurements and a generated graph recorded alongside the captured output.
