# Q4 — Medicine inventory collection benchmark

## Aim

Model medicines by code, name, quantity, and price; compare `HashMap`,
`TreeMap`, and `LinkedHashMap` for insertion, retrieval, batches of 100,000
lookups, and full iteration at inventory sizes 1,000, 10,000, and 100,000.
Choose a collection using measured performance and its ordering requirements.

## Prediction

`HashMap` should be fastest on average for code-keyed lookup when no order is
required. `LinkedHashMap` should retain insertion order at a modest memory and
update cost. `TreeMap` should be slower for updates and lookup but maintain
sorted code order without a separate sort.

## Design and test data

* Sources: `Q4/Medicine.java`, `Q4/PharmacyInventory.java`, and `Q4/InventoryBenchmark.java`. The `HashMapDemo`, `TreeMapDemo`, and `LinkedHashMapDemo` classes illustrate the respective inventory order/lookups; `MapBenchmark` is the benchmark entry point.
* Each deterministic dataset has unique `MEDnnnnnn` codes and corresponding
  names, quantities, and prices. Each dataset is shuffled with a fixed seed;
  every collection and repetition at a given size uses that same list and
  insertion order. All lookup keys are existing codes, in a deterministic
  mixed sequence of 100,000 operations.
* Each measured repetition times: insertion of all records into an empty map;
  100,000 repeated `get` calls for one fixed key (reported as average ns/op);
  100,000 lookups spread across the inventory; and one full values iteration.
  Map setup, data generation, and query-index generation are outside timed
  regions. A checksum consumes read results.
* Two warmups run per size/collection, followed by five measured repetitions.
  Each timed section uses `System.nanoTime()`. The CSV contains each measured
  trial, not generated estimates.

`Q4/output.txt`, and writes the actual sample reports to

### Lookup SLA and recommendation

For this controlled in-memory workload, define the acceptance target as a
**median no greater than 100 ms for 100,000 successful lookups** (1 microsecond
per lookup on average). All measured medians and individual trials pass. This
is a benchmark acceptance threshold, not a production end-to-end or tail
latency guarantee. The result supports `HashMap` for the expected code-keyed
workload when order is unnecessary; it had the fastest 100k mixed-lookups and
iteration and lowest 100k insertion time in these measurements. Use `TreeMap`
if continuous sorted-by-code traversal is worth its measured lookup/update
cost; use `LinkedHashMap` when insertion-order reporting is required.

## Alternatives and complexity

| Structure | Expected lookup / insert | Iteration / ordering | Space and trade-off |
|---|---|---|---|
| `HashMap` | Average O(1); collisions may make it slower, with tree bins in modern Java for eligible heavily-colliding buckets | O(capacity + n); no guaranteed order | O(n), hash table plus entries |
| `LinkedHashMap` | Average O(1) | O(n), insertion order | O(n) with extra before/after links |
| `TreeMap` | O(log n) | O(n), sorted by key | O(n) tree nodes and links |
| `Hashtable` | Average O(1), with collision and synchronization costs | O(capacity + n); no sorted order | O(n); synchronized legacy map, usually prefer modern map choices |
| Sorted array + binary search | O(log n) lookup; arbitrary insert O(n) | O(n), naturally sorted | O(n), compact storage; insertion shifts array elements |

The benchmark compares the first three implementations directly; `Hashtable`
and sorted-array results are analytical alternatives, not measured claims.
The collection choice therefore depends on order and update requirements as
well as the timings.

## Measurement limits and conclusion

The repeated fixed-key `get` is deliberately cache-hot, and the mixed batch is
an all-hit, deterministic synthetic workload. Nanosecond timings vary with
JIT compilation, garbage collection, CPU scheduling, JVM, and machine; the
smallest per-operation values are averages over a loop, not isolated-call
latencies. Five repetitions and medians reduce but do not eliminate noise.
For production SLAs, repeat on the deployment JVM and representative hardware,
include realistic hit/miss ratios and concurrent access, and measure latency
distributions. Within the defined experiment, `HashMap` is the recommended
default when sorting/insertion ordering is not a requirement.
