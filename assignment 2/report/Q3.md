# Q3 — Student identity and Java collections

## Aim

Treat a student's registration number (`regNo`) as identity, remove duplicate
students correctly, and compare scans, `HashSet`, `TreeSet`, and a
registration-keyed `HashMap`. Demonstrate why `equals` and `hashCode` must be
implemented together and why a key's identity must not change while it is in a
hash collection.

## Prediction

The legacy class that overrides `equals` only will allow two equal registrations
into a `HashSet`, because the set uses hash codes to locate candidate entries.
Adding a matching `hashCode` should reduce the sample to two unique students.
The list scan will find matches but take linear time; hash collections should
have average constant-time lookup, while a `TreeSet` will preserve sorted
registration order with logarithmic operations.

## Design and test data

`Q3/Student.java` defines the corrected student; `Q3/Attendance.java` provides
a small attendance set; `Q3/StudentCollectionsDemo.java` includes a legacy
equals-only student and exercises all three collection alternatives. Both
student versions compare registration numbers only. The sample contains three
objects: S101 twice (with different names) and S102 once. It then tests a normal
list `contains` scan, explicitly counts duplicate scan matches, inserts into all
three collection choices, mutates a registration number after insertion, and
uses the distinct strings `Aa` and `BB` to demonstrate a hash collision.

## Results

| Test | Actual result |
|---|---|
| Legacy `equals`-only `HashSet` | Size 3; incorrect for the two registration identities |
| Normal list scan for S101 | Found |
| Duplicate scan for S101 | 2 matches |
| Corrected `HashSet` | `Unique students: 2` |
| `TreeSet` with registration comparator | 2 |
| `HashMap<String, Student>` keyed by registration | 2; S102 lookup found |
| Mutated key in `HashSet` | `contains` and `remove` both false after changing S200 to S201 |
| `Aa` / `BB` collision | Equal hash codes, but both distinct students retained (set size 2) |

The `Aa`/`BB` case shows that collisions are permitted: unequal objects may
share a hash code, and `equals` still determines whether they are duplicates.

## Alternatives, contracts, and complexity

* **Linear scan (`List.contains` / loop):** O(n) per search; O(n) storage.
  Simple and suitable for small collections or scans requiring custom logic.
  A list accepts duplicates, so a separate check is needed before adding.
* **`HashSet<Student>`:** average O(1) add/search/remove and O(n) storage;
  iteration is O(capacity + n). Collisions can degrade operations (up to O(n)
  in the general case). It is the natural choice for uniqueness without
  ordering.
* **`TreeSet<Student>`:** O(log n) add/search/remove and O(n) storage. It returns
  sorted registration order and iterates in O(n). Its comparator must
  distinguish identities consistently with `equals`; otherwise it may silently
  treat distinct records as one.
* **`HashMap<String, Student>`:** average O(1) lookup/update by registration,
  O(capacity + n) iteration, and O(n) storage. Repeated registration keys
  replace the mapped student, which makes it useful for direct lookup. Using
  an immutable `String` key avoids depending on a mutable student object as the
  map key.

The `equals` contract requires reflexivity, symmetry, transitivity,
consistency, and false for `null`. Equal objects **must** return the same
`hashCode`; unequal objects need not have different hashes. `HashSet` and
`HashMap` first use a hash to locate a bucket and then equality to identify the
entry, so `equals` alone violates their contract. A changed hash-based key can
remain in its old bucket and become unreachable by normal lookup/removal.
Changing a value used by a `TreeSet` comparator can likewise invalidate its
ordering.

## Conclusion

The corrected `Student` implements both methods from the immutable-while-stored
identity field and the demonstration produces the required two unique
registrations. In production, make `regNo` immutable after construction (or
remove/reinsert after changing identity); prefer `HashSet` for deduplication,
`TreeSet` when sorted traversal is needed, and `HashMap<String, Student>` for
registration-keyed retrieval.
