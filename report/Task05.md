# Task 05 - Static Members and Object Life Cycle

## Aim
Generate unique ticket identifiers and understand class-level state and object references.

## Explanation
`ParkingTicket` has a static `AtomicLong` sequence. A static field belongs to the class, so all ticket objects share the same sequence; each constructor obtains a distinct number. A static method could expose facility-wide information without an instance, but this design keeps operations on their owning service/facility objects.

Local variables and collections hold object references. When the service removes a closed ticket and no other reachable object refers to it, that object becomes eligible for garbage collection. Java decides when to reclaim it; calling `System.gc()` is only a request and is not required for correctness. Static references remain reachable for the lifetime of their class loader.

## Code and output
Unique number generation is implemented in [`ParkingTicket`](../src/parking/model/ParkingTicket.java); [`ObjectLifeCycleDemo`](../src/parking/app/ObjectLifeCycleDemo.java) demonstrates it and clears an object reference after service removal. The system test repeatedly creates tickets; generated values are unique, although the tests intentionally do not depend on a particular counter value.

```text
First ticket: T000001
Second ticket: T000002
First ticket removed from service; local reference cleared.
Garbage collection timing is managed by the JVM.
```

The output is captured in [`ticket-lifecycle.txt`](../outputs/ticket-lifecycle.txt).

## Alternative concept
A ticket number could be generated by a database sequence or UUID. A database sequence coordinates multiple application processes but requires a database; UUIDs avoid shared counters but are longer and less readable. The static sequence is simple for this single-process coursework application.

## Complexity
Atomic sequence increment is O(1) time and O(1) shared space per ticket. Creating a ticket takes O(1) time and space. The active-ticket map takes O(A) space.

## Result
Ticket IDs are centrally and uniquely sequenced within a running application, and object cleanup does not rely on manual deallocation.
